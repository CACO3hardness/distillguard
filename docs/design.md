# 设计说明

## 一、为什么做成闸门，而不是提醒

Skill 之间没有调用钩子。一个"合规提醒"skill 是否被调用，取决于模型当时的判断；
而合规恰恰不能建立在"模型记得"之上。

所以这里换了一个做法：不让模型决定要不要遵守，而是**改变它能读到的文件**。
闸门产出 `approved/`，蒸馏工具只指向这个目录。被拦下的材料不在里面，读不到就是读不到。

代价是必须由使用者先填一份材料清单。这是有意为之：判断材料是否含第三人信息，
本来就不该由工具替使用者拍板。

## 二、为什么用确定性规则，而不是让大模型判断

三个理由：

1. **可复核。** 同一条规则跑两次结果相同，评审可以逐条对照 YAML。
2. **可解释。** 拦截理由是规则 ID，不是"模型觉得"。
3. **不容易被说服。** 大模型可以被一段漂亮的说明文字说服，规则表不会。

大模型适合做的部分（第三人识别、语义判断）恰恰是这里最不该自动化的部分——
漏掉一个姓名，整套机制就失效了。

## 三、fail-closed 的三处体现

| 情形 | 处理 |
|---|---|
| 清单字段缺失 | 按禁止处理，记 RF-08 |
| 材料类型无法归类 | 按禁止处理 |
| 同意要件无法确认 | 挂起，不进入 approved |

## 四、与相邻工具的区别

| 工具类型 | 管什么 | 不管什么 |
|---|---|---|
| PII 脱敏工具 | 找出并替换身份证号、手机号 | 不判断"这段判断方式该不该被提取" |
| 合规清单文档 | 列出应该做什么 | 不保证真的做了 |
| **本工具** | 决定什么材料能进入提取，并要求出厂条件可核查 | 不判断法律效力，不生成同意书 |

## 五、红旗清单的由来

研究报告第五章对方案本身做了反思：分层清单可能被形式化，企业加一份同意书，
实质的提取范围没有变化。本工具把这段反思变成可检测的规则：

- 概括性授权 → RF-01
- 压力峰值签署 → RF-02
- 无退出机制 → RF-03
- 无到期时间 → RF-04
- 第三人未隔离 → RF-05
- 以工作任务替代授权 → RF-06
- 对价未单列 → RF-07

如果只输出"合规/不合规"，工具会变成洗白模板；输出红旗，它才站在被提取者一边。

## 六、没有做的事

- 没有做自动第三人识别：靠申报 + 模式提示，拿不准就拦。
- 没有做 UI：命令行足够演示，也更容易被审计。
- 没有接模型：规则是确定的，接模型只会让结果不可复现。
